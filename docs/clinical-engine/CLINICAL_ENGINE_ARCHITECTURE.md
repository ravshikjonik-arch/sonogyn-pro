# SonoGyn Clinical Engine — целевая архитектура

**Статус:** проект на утверждение (2026-11-06). Реализации нет.
**Принцип:** не новый движок, а **общий контракт + адаптеры существующих движков + единый UI + реестр версий**.
Опирается на: [ARCHITECTURE_AUDIT.md](./ARCHITECTURE_AUDIT.md), [CALCULATOR_CONTRACT.md](./CALCULATOR_CONTRACT.md), ADR Medical Intelligence (MI-21: движки вызываются напрямую через публичные API).

## 2. A. Реестр рекомендаций

- **Источник истины для метаданных** — существующие таблицы Supabase `sources` и `canonical_calculator_registry` (+ `_versions`, `_sources`). Новых таблиц не создаём; недостающие поля (дата следующей проверки, статус клинической проверки) — отдельной обратимой миграцией по согласованию.
- **В коде** каждый движок экспортирует неизменяемую ссылку `GuidelineRef` (`{ id, organization, title, version, publishedAt, officialUrl }`). Реестр в БД сверяется с ней тестом.
- Разные версии рекомендаций = разные `algorithmId` (`orads-us@2022`, будущий `orads-us@20xx`), никогда не объединяются.
- Детали — [GUIDELINES_REGISTRY.md](./GUIDELINES_REGISTRY.md).

## 3. B. Детерминированный движок

- Остаются **существующие** функции (`evaluateOradsUs2022`, `calculateAdnex`, `evaluateAcrTirads`, …). Формулы и пороги не меняются в рамках архитектурной работы.
- Каждый пакет получает подпуть `./contract` (тонкий адаптер): `evaluate(input: ClinicalInput) → ClinicalResult`. Адаптер:
  - проверяет вход Zod-схемой (строгой, без неизвестных полей);
  - различает `value` / `not_assessed` / `not_provided` / `not_applicable` для каждого признака;
  - **никогда не подставляет значения по умолчанию**; если движку нужен признак, а его нет — статус `incomplete` с перечнем;
  - возвращает пошаговое обоснование (`explanation[]`) из движка, а не из LLM.
- Без зависимостей от AI SDK, сети, БД, `Date.now()`/`Math.random()` — чистые функции, одинаковый вход → одинаковый результат.
- Zod-схемы входов — в самих пакетах движков (рядом с типами), общие примитивы — в `packages/types`.

## 4. C. Динамический UI

- Калькулятор описывается **декларативной спецификацией вопросов** (`CalculatorSpec`, см. контракт): блоки, условия показа, единицы, подсказки, схемы.
- Для O-RADS спецификация строится на основе существующего навигатора `orads-us/src/navigator` (дерево ACR-стиля) — он уже даёт «один вопрос за раз».
- Один рендерер на платформу (web / mobile), общий пакет спецификаций и движков; визуальные компоненты — на дизайн-токенах клиники (light/dark).
- Детали — [UX_DESIGN_PRINCIPLES.md](./UX_DESIGN_PRINCIPLES.md).

## 5. D. Единый результат

`ClinicalResult` (см. контракт): статус (`calculated | incomplete | invalid | not_applicable`), основное значение (категория, балл, вероятность, перцентиль — тип зависит от калькулятора), интерпретация, рекомендации, обоснование, версия руководства, первоисточники, ограничения, текст для протокола.
Совместимость: отображается в существующие `StructuredCalculatorBlockSchema` (протокол), `ClassificationSection` (MI), `ToolExecutionResult` (AI-чат) без изменения их публичной формы.

## 6. AI Evidence — отдельный слой

Разрешено: объяснять результат, находить рекомендации и источники, помогать с текстом заключения, объяснять параметры.
Запрещено (уже закреплено в TASK 05.2–05.4 и PR 1): выставлять категорию вместо движка, менять результат, подставлять недостающие данные, выбирать неподтверждённые правила. Категория в UI — только из `ClinicalResult` движка.

## 7. Подключение нового калькулятора

1. Запись в реестре (`GuidelineRef` + строка в `canonical_calculator_registry`).
2. Движок в своём пакете (или существующий) + `./contract` с Zod-схемой.
3. `CalculatorSpec` (вопросы, условия, единицы).
4. Тесты по [CLINICAL_VALIDATION_STANDARD.md](./CLINICAL_VALIDATION_STANDARD.md).
5. Регистрация в каталоге `packages/clinical-tools` (web/mobile ссылки).
Логика одного модуля не переиспользуется для другой классификации (O-RADS ≠ IOTA ≠ TI-RADS); общими являются только контракт, UI-рендерер и валидационный каркас.

## 8. Ограничения

- Не создаём дублирующие пакеты движков; FIGO, шейка, ПЭ, GA/EDD — **переносим** в существующие пакеты, а не пишем заново.
- Изменения клинических правил — только отдельными PR с первоисточником и клиническим подтверждением.
- Production-инцидент с `assetPrefix` и PR 1–4 — отдельные потоки; эта архитектура их не затрагивает.
